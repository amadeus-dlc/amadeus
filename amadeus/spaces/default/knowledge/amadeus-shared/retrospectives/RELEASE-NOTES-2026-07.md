# Amadeus-DLC 2026年7月 リリースノート

> 対象期間: 2026年7月1日〜7月31日 / リリース: v0.1.0 〜 v0.1.7(8回)

Amadeus-DLC は、AI に開発を任せるときの「勝手に進んでしまう」「なぜそう決めたか残らない」という問題を、工程と承認を仕組みで縛ることで解決するフレームワークです。7月は、**この仕組みが開発チームの手元だけで動く実験から、外部の人が自分の環境に入れて使える製品になった月**でした。

## 導入が「フォルダの手コピー」から1コマンドになった

7月最大の変化は導入方法です。それまでは配布物のフォルダを利用者が手でコピーする方式で、初回導入が面倒なうえ、いったん入れると更新する手段がなく、コピー漏れも防げませんでした。

7月8日の初回リリース(v0.1.0)にあわせてインストーラ `@amadeus-dlc/setup` を公開し、1コマンドで導入・更新できるようにしました。更新時は変更点を先に提示してから適用するため、利用者が独自に加えた設定を壊しません。

```bash
bunx @amadeus-dlc/setup install
```

対応するAI開発ツールも4種類から7種類へ広がりました。月初は Claude Code / Codex CLI / Kiro CLI / Kiro IDE の4種類でしたが、7月中旬に OpenCode と Cursor、下旬に Kimi Code を追加しています。「うちのチームが普段使っているツールでは動かない」という導入の壁がかなり下がりました。

あわせて月末には、README とドキュメント全体を実際の実装と1件ずつ突き合わせ、古い手順や存在しないコマンドで読者を迷わせる記述を洗い出して直しています。ドキュメントは全編が英語と日本語の対訳で、現在199ファイルです。

## AIエージェントのチーム開発が、正式機能になった

Amadeus には、複数のAIエージェントを別々の作業場で同時に動かし、設計判断を投票で決める「チームモード」があります。7月まではこれが開発チームの手元スクリプトに留まっていましたが、下旬に正式な製品機能として配布物に載せました。

判断を投票で決める部分も大きく変わりました。月半ばまでは票の集計と記録を人が目視で転記しており、数え間違いや記載漏れが1日に5件以上出ていました。これを専用ツールが担う形に切り替え、人とAIは判断そのものだけに集中できるようにしています。決定の履歴が後から書き換えられない形で残る点は、監査の観点でも意味があります。

チームの起動そのものも作り直しました。**起動にかかる時間は約200秒から約6秒へ短縮しています**(3人構成での実測)。さらに調査の過程で、それまで起動確認の仕組みが一度も実際には動いていなかったことが判明したため、これも本当に動くよう作り直しました。速くなっただけでなく、失敗したときにきちんと失敗とわかる状態になっています。

チームを組まない一人での利用者にも同じ恩恵が届くようにしました。AIが2体の独立した検証役を立てて多数決で判断する仕組みと、「この範囲は任せる」と事前に承認しておけば細かい確認を毎回繰り返さずに済む仕組みです。ただし重要な節目では必ず人が判断する、という原則は変えていません。

## 進捗が GitHub 上で自動的に最新になった

作業の進み具合を GitHub の Issue とプロジェクトボードへ自動的に映す機能(Intent Mirror)を、7月に一から作って実用段階まで持っていきました。月末には、ボード上のステータスも自動更新されます。

関係者にとっての意味はひとつで、**進捗を知るために誰かが手で更新する必要がなくなった**ことです。開いて見れば常に最新である、という状態になりました。

自動化の範囲は「切る / 都度確認する / 全自動」の3段階から選べます。全自動を選んだ場合でも、動くのは作業の節目だけで、常時監視するような仕組みは持っていません。

## 後から機能を足せるプラグインの仕組みが動き出した

全員に一律の機能を持たせるのではなく、必要なチームだけが必要な工程を足せるようにする「プラグイン」の仕組みを、7月下旬に構想から実用まで進めました。フォルダを置くだけで機能が増え、外すと痕跡なく元に戻ります。7種類すべての環境に対応しています。

最初のプラグインとして、並行処理の設計ミスを数学的に検証する高度な検査(TLA+ による形式検証)を用意しました。すべてのチームに必要なものではないため、まさにプラグインとして切り出す価値がある例です。

## 品質を数字で追えるようにし、実際に引き上げた

7月前半の時点では、品質が良くなっているかを裏づけるデータがなく、改善の効果を感覚でしか語れない状態でした。7月12日にコード量・複雑度・テスト数・網羅率を自動で記録する仕組みを入れ、下旬にはそれを1枚のグラフ画面として見られるようにしています。

蓄積したデータが示す7月後半の推移は次のとおりです。

- テストの自動検証項目: 4,599件 → 9,414件(約2倍)
- コードのテスト網羅率: 59.6% → 88.3%
- もっとも複雑な処理の複雑度: 65 → 43(低いほど読みやすく壊れにくい)

コード量は同期間に約2倍(約5万行 → 約9.6万行)に増えており、規模を倍にしながら網羅率を約30ポイント上げたことになります。

品質面ではもうひとつ、「検査が赤いときは本当に問題がある」と信じられる状態を取り戻す作業に相当量を投じました。実際には問題がないのに失敗する検査(いわゆる不安定なテスト)が続くと、開発側が警告を無視するようになり、本物の不具合が素通りしてしまうためです。月末には、実行時間に左右される性能テストを、変更をブロックする検査から夜間の定期実行へ切り離しました。

## バグを「見つけては直す」の無限ループに、停止条件を入れた

7月に見つかった不具合の多くは、書き間違いではなく**仕様の穴**でした。正しさの判断基準が最初から出そろっていないため、望ましくない挙動がいつまでも見つかり続け、修正が終わらないという構造です。

そこで7月20日から、この構造そのものを止める方法を実測で選ぶ実験を行いました。実際に起きた欠陥7件を題材に、検証方法を2つ用意して同じ条件で比べたところ、**数学的な網羅検証(TLA+)は7件すべてを検出し、もう一方の手法は7件中3件しか検出できませんでした**。見逃した4件は、検証する側と検証される側が同じ勘違いをしていたために互いに打ち消し合った、というのが原因です。

この結果を受けて、日常の検査は従来どおり軽量なテストで回し、並行処理のように順序が絡む重要な部分の仕様を変えるときだけ数学的検証を追加する、という二段構えの方針を採用しました。

## 積み上がった「学習」

Amadeus は、人が指摘した内容をルールとして蓄積し、同じ失敗を繰り返さないようにする仕組みを持っています。7月末時点で406件のルールが積み上がりました。すべて、実際に起きた問題とその証拠に紐づいています。

このフレームワーク自身が Amadeus を使って開発されており、7月に完了した105件の開発テーマはすべて、自らの工程・承認ゲート・監査記録を通っています。作った仕組みを毎日自分たちで使い倒したことが、これだけの改善点が見つかった理由でもあります。

月末時点で未解決の課題は30件です。7月に561件を起票して489件を解決しているため、見つけたそばから片づけている状態は保てています。
