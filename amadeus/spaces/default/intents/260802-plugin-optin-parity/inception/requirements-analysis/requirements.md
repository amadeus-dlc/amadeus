# Requirements Analysis — Issue #2018

## 1. 目的

GitHub Issue [#2018](https://github.com/amadeus-dlc/amadeus/issues/2018) で報告された、plugin を導入する意思がプロジェクトに記録されず、新しい worktree や別ハーネスで必要な plugin が導入されない不具合を修正する。

本対応は `self-fix` とする。新しい plugin 機能を追加するのではなく、既存の供給・導入・合成・有効化の流れを、Claude、Codex、Cursor、OpenCode、Kimi、Kiro CLI、Kiro IDE で同じ契約に戻す。

## 3. 用語と対象範囲

- **導入対象の plugin 名**: このプロジェクトで各ハーネスへ導入すると利用者が明示した plugin 名。project root の `amadeus/config.json` に記録する。
- **供給元**: リポジトリで管理する `plugins/<name>/`。
- **ハーネス別の導入元ファイル**: 現在のハーネス配下にある `.amadeus-plugin-src/<name>/`。供給元から決定的に生成する。
- **合成結果の記録**: 現在のハーネス配下にある `.amadeus-plugin-composition.json`。導入元ファイルをハーネス固有の成果物へ合成した結果を表す。
- **対象ハーネス**: Claude、Codex、Cursor、OpenCode、Kimi、Kiro CLI、Kiro IDE。Kiro CLI と Kiro IDE は同じ `.kiro` 配下の状態を共有するため、7つの利用面に対して6つのハーネスディレクトリを扱う。

## 4. 機能要件

### FR-1: 導入対象を project root に記録する

1. `amadeus/config.json` は、導入対象の plugin 名を `plugins` キーの配列として保持しなければならない。設定例は次のとおりとする。

   ```json
   {
     "plugins": ["formal-model-check"]
   }
   ```

2. この設定は project root の `amadeus/config.json` だけを正本とし、space または intent の設定では上書きしない。
3. plugin 名は1文字以上64文字以下とし、正規表現 `^[a-z0-9](?:[a-z0-9-]{0,62}[a-z0-9])?$` に一致しなければならない。大文字、空白、Unicode、先頭・末尾のハイフン、区切り文字、`.`、`..` は受理せず、大小文字変換や空白除去による暗黙の補正も行わない。
4. 配列は記載順に意味を持たず、plugin 名の昇順に正規化して処理する。重複、型違い、不正な plugin 名を受理してはならない。
5. 設定キーがない場合と空配列の場合は、どちらも「導入対象なし」という明示的な正常状態として扱わなければならない。
6. `plugins/<name>/` が存在するだけでは導入対象とみなしてはならない。
7. 設定された plugin の供給元が存在しない場合は、利用者に plugin 名と不足箇所が分かる劣化状態を提示し、導入済みとして扱ってはならない。
8. `plugins` キーを space または intent の `config.json` に記載した場合は設定エラーとし、project root の設定だけが有効であることを示さなければならない。

### FR-1A: 既存コマンドと project 設定を同期する

1. `install <path>` は、入力を検証した後、plugin の供給元を project root の `plugins/<name>/` に永続化し、`amadeus/config.json` の `plugins` へ plugin 名を追加し、現在のハーネスへ導入・合成する1つの操作として扱わなければならない。
2. `install <path>` の全処理が成功するまで `plugins` の変更を確定してはならない。失敗時は、既存の設定、供給元、現在のハーネスの導入元ファイル、合成結果を実行前と同じ状態に戻さなければならない。
3. 既に同じ供給元と同じ plugin 名が設定されている場合の `install <path>` は正常な冪等操作とする。異なる供給元を同名で置き換える場合だけ、既存どおり `--force` を要求する。
4. `drop <plugin-name>` は、現在のハーネスから当該 plugin を安全に削除できた後に、project root の `plugins` から plugin 名を削除しなければならない。供給元 `plugins/<name>/` は履歴・再選択のため削除しない。
5. `drop <plugin-name>` が失敗した場合は、project root の `plugins` から plugin 名を削除してはならない。
6. `compose`、`compose --if-stale`、`doctor`、`status` は `amadeus/config.json` を変更してはならない。
7. 利用者が `amadeus/config.json` を直接編集する操作も正式にサポートし、次の自動導入で現在のハーネスをその内容へ再調整しなければならない。

### FR-2: 現在のハーネスへ自動導入する

1. 各対象ハーネスは、セッション開始時または公式に提供される同等のライフサイクルイベントで、`amadeus/config.json` の導入対象を読み取らなければならない。
2. 各対象ハーネスは、現在使っている自ハーネスだけについて、供給元からハーネス別の導入元ファイルを生成し、既存の合成処理を実行しなければならない。他ハーネスのディレクトリを同時に変更してはならない。
3. 新しい worktree でハーネス別の導入元ファイルと合成結果の記録がまだ0件でも、導入対象が設定されていれば、処理を省略せず必要な状態を生成しなければならない。
4. 同じ設定と同じ供給元で処理を繰り返した場合、生成物を不要に変更してはならない。
5. 導入対象から plugin 名を削除した場合は、現在のハーネスにある Amadeus 管理下の当該 plugin 導入元と合成結果を再調整しなければならない。利用者管理のファイルや無関係な plugin を削除してはならない。
6. OpenCode は例外扱いにせず、公式の JavaScript／TypeScript plugin フックから Amadeus の自動導入処理を呼び出さなければならない。利用者による明示的な `compose` を初回利用の前提にしてはならない。
7. 前項は、Reverse Engineering 時点で記録された OpenCode の `manual-only` という現行分類を、利用者のQ2回答で明示的に廃止する裁定である。OpenCodeが `session.created` を含む公式セッションイベントと既存のAmadeus pluginフックを提供しており、技術的制約ではなくAmadeus側の未配線だと確認できたため、他ハーネスと同じ自動導入契約を優先する。

### FR-2A: 自動導入の失敗と原子性

1. 自動導入は、設定全体と全導入対象の供給元を変更前に検証しなければならない。設定不正または供給元不足が1件でもある場合、現在のハーネスを変更せず、全体を劣化状態として扱わなければならない。
2. 事前検証後の導入・合成は plugin ごとの既存トランザクション境界で実行する。ある plugin が失敗する前に別の plugin が正常に確定済みであれば、その正常な確定を巻き戻す必要はない。
3. 失敗した plugin は、導入元ファイル、所有ファイル、合成結果の記録のいずれにも部分状態を残してはならない。合成結果の記録には正常に確定した plugin だけを記録する。
4. 1件でも失敗した場合、CLI は非0で終了し、セッション開始フックは対象ハーネスとplugin名を含む警告を1回以上表示した上でセッション自体は継続する。`doctor` は全体を劣化状態とし、成功済みと失敗したpluginを個別に表示する。
5. 次のセッション開始時は、正常に確定した plugin を変更せず、未完了または古い plugin だけを再試行しなければならない。

### FR-3: 導入状態を正しく判定し、診断できるようにする

1. 導入状態の判定は、`amadeus/config.json` の導入対象、供給元、現在のハーネスにある導入元ファイル、合成結果の記録を比較しなければならない。
2. 導入対象が1件以上ある状態で、現在のハーネスの導入元ファイルと合成結果の記録がともに0件である場合、これを最新状態と判定してはならない。
3. 導入対象が0件で、Amadeus 管理下の残存物もない場合は、正常かつ変更不要と判定しなければならない。
4. `doctor` は、少なくとも「導入対象なし」「導入未完了」「供給元不足」「合成結果が古い」「導入済み」を区別し、問題となる plugin 名と現在のハーネスを表示できなければならない。
5. 自動導入に失敗した場合は黙って継続せず、利用者が原因と次に確認すべき対象を特定できる情報を提示しなければならない。

導入状態の正規化結果は次の表に従う。

| code | 条件 | 自動導入 | `doctor` | セッション開始結果 |
|---|---|---|---|---|
| `not-selected` | `plugins` が空で管理下の残存物なし | 変更なし | 正常・導入対象なし | 無警告で継続 |
| `source-missing` | 選択済みだが `plugins/<name>/` がない | 変更前に中止 | 劣化・供給元不足 | 警告して継続 |
| `not-installed` | 選択済み・供給元あり・現在のハーネスの導入元なし | 導入して合成 | 成功後は `current` | 成功なら無警告、失敗なら警告して継続 |
| `stale` | 導入元または合成結果が供給元・設定と不一致 | 再調整して合成 | 成功後は `current` | 成功なら無警告、失敗なら警告して継続 |
| `current` | 選択、供給元、導入元、合成結果が一致 | 変更なし | 正常・導入済み | 無警告で継続 |
| `failed` | 導入または合成トランザクションが失敗 | 未完了分を残さない | 劣化・失敗段階 | 警告して継続 |

### FR-4: plugin の有効化判定を全ハーネスで揃える

1. 導入された plugin が定義する判定と案内は、対象ハーネスすべてで同じ意味を持たなければならない。
2. formal-model-check plugin の検査要否は、Requirements Analysis、Functional Design、Build and Test の各チェックポイントで判定しなければならない。
3. 前項の判定は、通常ワークフローと単一ステージ実行の両方で同じ結果にならなければならない。
4. 自動導入処理は plugin を利用可能にするところまでとし、TLC を含む形式検査を自動実行してはならない。
5. formal-model-check の正規化結果は `not-ready`、`never-run`、`changed`、`current` とする。通常ワークフローと単一ステージ実行は、少なくとも `plugin`、`checkpoint`、`code`、対象または不足理由を同じ構造化値で返さなければならない。表示文の装飾だけはハーネス固有でもよい。
6. `not-ready` は宣言済みの有効な検査対象がない状態、`never-run` は対象があるが成功記録がない状態、`changed` は対象が成功記録後に変化した状態、`current` は対象と成功記録が一致する状態とする。
7. `not-ready`、`never-run`、`changed` では人間が次の操作を判断できる案内を返し、`current` では案内を返さない。pluginが選択されていない場合も案内を返さない。

### FR-5: 初回導入と検査成功を分離する

1. formal-model-check plugin は、検査対象の仕様ファイルが0件でも導入と合成に成功しなければならない。
2. 検査に必要な対象が揃っていない間は「未準備」として案内し、検査成功または「前回から変更なし」を記録してはならない。
3. 利用者が形式検査を明示的に実行した場合は、`specs/tla/model-map.json` が宣言する有効なモデルと設定が存在するまで、理由を示してエラーにしなければならない。
4. 過去に検査成功を記録した後で、宣言済みの対象が削除または無効化された場合は、過去の記録だけを根拠に最新状態または成功状態として扱ってはならない。

### FR-6: 既存プロジェクトとの互換性を維持する

1. 導入対象を設定していないプロジェクトでは、既存の起動、ステージ実行、`doctor`、配布成果物に実質的な副作用を追加してはならない。
2. 既存の明示的な plugin の導入、合成、削除コマンドは、自動導入と矛盾しない範囲で引き続き利用できなければならない。
3. 既存のハーネス別合成規則、所有境界、配布時の生成規則を維持しなければならない。

## 5. 非機能要件

### NFR-1: 決定性と冪等性

- 同じ project 設定、同じ供給元、同じハーネスからは同じ導入元ファイルと合成結果が得られなければならない。
- 自動導入を複数回実行しても、意味のない差分や重複登録を発生させてはならない。

### NFR-2: 安全性

- plugin 名から解決するパスは、許可された `plugins/` と現在のハーネスの管理対象ディレクトリを越えてはならない。
- Amadeus 管理下であることを確認できない既存ファイルを上書きまたは削除してはならない。
- 不正な設定または供給元不足は全体を変更前に fail-closed とする。合成失敗は plugin 単位で fail-closed とし、失敗した plugin の部分状態だけを確定してはならない。

### NFR-3: 移植性

- Bun を使う既存の短命CLI・フック構成を維持し、macOS、Linux、native Windows PowerShell で動作しなければならない。
- ハーネス間で共有する判断は framework core に置き、ハーネス固有部分はライフサイクルへの接続と成果物形式に限定しなければならない。

### NFR-4: 性能

- セッション開始時の処理は、設定、供給元のメタデータ、導入元ファイル、合成結果の比較に限定し、形式検査や無関係な全ハーネス再生成を行ってはならない。
- 同一runner上で変更前の `main` と変更後を各100回測定したとき、導入対象なしと `current` の冪等再実行について、p95の増加は変更前の20%または25msの大きい方を超えてはならない。
- 初回導入について、既存の明示的な `install` と `compose` を連続実行する基準経路と変更後の自動導入を同一fixtureで各30回測定したとき、p95の増加は基準経路の20%または50msの大きい方を超えてはならない。

### NFR-5: 可観測性

- 自動導入の実行、変更不要、未準備、失敗を区別できる結果を返さなければならない。
- エラーと `doctor` の出力は、対象ハーネス、plugin 名、欠けている状態を含まなければならない。

## 6. 検証要件

テスト戦略は **Comprehensive** とする。

1. `amadeus/config.json` の設定について、キーなし、空配列、1件、複数件、重複、型違い、不正な plugin 名、供給元不足を単体テストする。
   `plugins` キーの記載場所、順序の無意味性、大小文字・空白・Unicodeを補正せず拒否することも含める。
2. Claude、Codex、Cursor、OpenCode、Kimi、Kiro CLI、Kiro IDE の各利用面について、新しい worktree の0件状態から、現在のハーネスだけに導入元ファイルと合成結果が生成されることを統合テストする。
3. OpenCode の公式 plugin フックが初回セッションで自動導入を起動し、明示的な `compose` なしで plugin が利用可能になることを統合テストする。
4. 導入対象なしのリポジトリでは、全対象ハーネスで変更が発生しないことを回帰テストする。
5. 設定追加、供給元変更、設定削除、供給元不足、途中失敗、再実行について、判定と再調整が決定的かつ冪等であることをテストする。
6. Requirements Analysis、Functional Design、Build and Test の各チェックポイントについて、通常ワークフローと単一ステージ実行の双方で同じ案内が得られることをテストする。
7. formal-model-check plugin について、仕様0件で導入成功、未準備表示、成功記録なし、明示検査失敗、対象追加後の検査成功、対象削除後の未準備復帰をテストする。
8. `doctor` が正常状態と各異常状態を区別し、対象ハーネスと plugin 名を報告することをテストする。
9. 既存の plugin 合成、形式検査、ハーネス配布に関する回帰テストを維持し、`bun scripts/package.ts --check` と `bun run promote:self:check` の drift guard を通す。
10. `install`、`drop`、`compose` と project root の `plugins` 設定の同期規則、および失敗時に実行前状態へ戻ることを統合テストする。
11. 導入状態とformal-model-check結果の各 `code`、警告有無、CLI終了値、`doctor`表示を状態表どおりにテストする。
12. 7つの利用面について初回導入と冪等再実行の性能を同一runner上で測定し、NFR-4の退行上限内であることを確認する。

## 7. 受け入れ条件

1. project root の `amadeus/config.json` に plugin 名を設定した新しい worktree で、最初のセッションから現在のハーネスへ必要な plugin が自動導入される。
2. 前項は7つの対象利用面すべてで成立し、OpenCode だけに明示的な `compose` を要求しない。
3. 導入対象ありの0件状態と、導入対象なしの正常な0件状態を区別できる。
4. 導入対象の plugin が欠けている、古い、または供給元を解決できない場合、起動時または `doctor` で黙らずに診断される。
5. formal-model-check plugin は仕様0件でも導入できるが、対象が揃うまで検査成功や「変更なし」を記録せず、明示検査はエラーになる。
6. 3つのチェックポイントと通常・単一ステージ実行で、plugin の案内が全ハーネス同義になる。
7. 導入対象を設定していない既存プロジェクトでは、動作と生成物に不要な変更がない。
8. 自動導入によって TLC が実行されない。

## 8. 制約と対象外

- `dist/` や昇格後の生成領域は手編集せず、framework source を変更してパッケージ生成で同期する。
- plugin のマーケットプレイス、外部からの自動取得、依存解決機構は追加しない。
- 導入対象の plugin 名を space または intent ごとに切り替える機能は追加しない。
- 1つのハーネスの開始イベントから、他ハーネスの成果物を先回りして変更しない。
- TLC などの形式検査をセッション開始時またはステージ開始時に自動実行しない。
- 未定義用語の検出は [#2029](https://github.com/amadeus-dlc/amadeus/issues/2029)、用語定義の正本統一は [#2030](https://github.com/amadeus-dlc/amadeus/issues/2030) で扱い、本 Issue の実装範囲に含めない。

## 9. 前提

- 各配布パッケージには、自動導入処理を呼び出すために必要な Amadeus のハーネスアダプターが含まれる。
- `plugins/<name>/` は、プロジェクトが管理する plugin の供給元として引き続き利用できる。
- OpenCode は公式 plugin API でセッションイベントを受け取れ、既存の Amadeus OpenCode plugin から自動導入処理を呼び出せる。
- Kiro CLI と Kiro IDE は同一の `.kiro` 配下を共有するが、それぞれの利用面から同じ導入状態を観測できる。
