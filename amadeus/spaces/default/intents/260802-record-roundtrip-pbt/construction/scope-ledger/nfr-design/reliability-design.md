## 0. 本 unit で信頼性が実質論点になる理由

本 unit の成果物は実行されない Markdown 文書1件であり、稼働率・障害復旧・リトライといった通常の信頼性関心を持たない。にもかかわらず信頼性設計が実質的に必要になるのは、business-logic-model.md §2「対象境界と出典(正本の所在)」が台帳の内容を**すべて外部の可変資源(GitHub Issue 本文)からの転記**と定めているためである。同節の表は、9件の1行要約の正本を `Issue #1980 本文 \`## 背景・実測\` の箇条 9 行(取得本文 \`:16-24\`)`、射程判定の正本を `Issue #1980 本文 \`## 関連\` の分類行(取得本文 \`:72\`)` と置いている。

したがって本 unit の信頼性課題は次の2点に収斂する。

- **F-1 出典揮発**: 引用元(Issue 本文)がリモートで改稿・削除され、行番号引用が別内容を指すか解決不能になる。
- **F-2 検査不能化**: 台帳の正しさを後から確かめる手段が、揮発しうる資源への再アクセスに依存してしまう。

以下はこの2点への設計であり、それ以外の信頼性カテゴリは §5 で N/A を根拠付きで宣言する。

## 1. F-1 出典揮発への耐性 — 三点併記規則(BR-SL-10 の設計面)

business-rules.md `:24` BR-SL-10 実文は `出典引用には**取得日と取得コマンド**を台帳冒頭に明記する。Issue 本文はリモートで改稿されうるため、行番号だけの引用にしない` であり、検査列は `台帳冒頭に \`gh issue view 1980\` と取得日を含む測定 ref 行が実在` と定める。本設計はこれを、**行番号・取得メタ・verbatim 断片の三点併記**として具体化する。

| 併記要素 | 役割 | 揮発時の挙動 |
| --- | --- | --- |
| (a) locator(行番号 `:72` 等) | 取得時点の位置の記録 | 改稿で無効化しうる(単独では復元不能) |
| (b) 取得メタ(取得コマンド + 取得日) | 断面の同定 | 改稿されても「どの断面か」は残る |
| (c) verbatim 断片 | 内容の同定 | 改稿後も**全文検索で再解決できる**。改稿されていれば不一致として検出できる |

三点のうち (c) が復元能力の中核である。(a) 単独は改稿で無音に別内容を指し、(b) 単独は内容を復元しない。(a)+(b)+(c) が揃って初めて「当時この文言がここにあった」という主張が反証可能になる。

domain-entities.md `:84` の `SourceCite = { origin: "requirements.md" | "#1980本文", locator: string, retrievedAt?: ISO日付 }` と、同 `:87` 実文 `\`#1980本文\` を origin とする引用は \`retrievedAt\` を必須とする(リモート本文は改稿されうる — BR-SL-10)。repo 内成果物を origin とする引用は測定 ref(HEAD SHA)で代替する。` が (a)(b) を型として与えている。本設計はここへ (c) を**必須**として足す:

- **R-1**: `origin` が `#1980本文` の引用は、locator と retrievedAt に加えて **verbatim 断片を必ず併記する**。断片は装飾(強調記号・全角括弧の有無)に依存しない核心部分文字列を選ぶ — 装飾は改稿で最も変わりやすく、断片照合の偽陰性源になるため。
- **R-2**: `origin` が repo 内成果物(requirements.md 等)の引用は、**測定 ref(HEAD SHA)を断面同定に用いる**。Git 履歴が断面を保存するため verbatim 断片は必須ではないが、business-logic-model.md §2 の表が既に実施しているとおり併記を推奨する。
- **R-3**: 取得コマンドは実行した形をそのまま書く(`gh issue view 1980 --json title,body`)。要約した擬似コマンドを書かない — 再取得が同じ断面を返す保証が失われる。

**embedded fallback を持たない**: Issue 本文のスナップショット全文を台帳や record へ複製して「原本が消えてもこちらがある」とする案は採らない。cid:nfr-design:c3(Git 管理資産では埋め込み fallback を二重保持せず、単一ソースと drift 検出を優先する)に反し、原本と複製の drift が新しい失敗モードになるためである。本設計が保持するのは全文複製ではなく**照合に足る最小断片**であり、これは二重保持ではなく引用である。

## 2. F-2 検査可能性 — ローカル完結の fail-closed 検査

business-logic-model.md §5 の不変量表(A1〜A5)は、合否検査を `test -f` / `grep -c` / 行数照合という決定的手順で定めている。本設計はこの検査集合が**ネットワークアクセスを一切必要としない**ことを設計上の要件として固定する。

| 検査 | business-logic-model.md §5 の定義 | 外部依存 |
| --- | --- | --- |
| A1 | `test -f amadeus/spaces/default/intents/260802-record-roundtrip-pbt/bug-scope-ledger.md` | なし(ローカル FS) |
| A2 | 9 番号それぞれの `grep -c` が 1 以上、かつ番号の異なり数が 9 | なし |
| A3 | 台帳表の行数が 9、各行の判定列が語彙 3 値のいずれか | なし |
| A4 | 表の行数 = 9 | なし |
| A5 | §4 の写像表と台帳の判定列が全 9 行で一致 | なし(写像表は record 内に固定済み) |

- **R-4**: A1〜A5 のいずれも `gh` / ネットワークを呼ばない。台帳の受入判定が GitHub の可用性・認証状態・rate limit に依存しない。business-logic-model.md §4 が判定写像 M を **FD 段で固定**し実装段で再導出しないと定めている(同節 実文 `FD 段でこの表を固定し、実装(執筆)段では**判定を再導出しない**。`)ことが、この独立性を構造的に成立させている — 判定の正本が record 内へ既に写し取られているため、受入判定に原本は要らない。
- **R-5**(fail-closed): 検査が1つでも不通過なら受入不可とし、部分受理を作らない。business-logic-model.md §3 `[S4]` 実文 `A1〜A3 全通過で受入可。1つでも不通過なら S1 へ戻す(部分受理を作らない)` および同 §3 末尾 実文 `中間状態 S2 で止めた文書(行が欠けた台帳)を成果物として提出しない` がこの姿勢を既に定めている。本設計はこれを A4・A5 まで拡張する(A4/A5 は business-logic-model.md §5 末尾が `FR-6a の合否を緩めない(追加のみ)` と位置づける派生検査であり、fail-closed 側へ寄せても FR-6a と矛盾しない)。
- **R-6**(検査の空文化防止): 検査が「0 件ヒットで exit 1」となる述語(`grep -c`)を `&&` 連鎖の中間に置かない。連鎖中の 0 件は後続を無音スキップさせる(cid:code-generation:no-grep-count-mid-chain)。検査は1つずつ独立ステップで実行し、それぞれの exit code を個別に読む。

## 6. 保証の層別(一枚岩の断定を避ける)

| 層 | 何を保証するか | 何を保証しないか |
| --- | --- | --- |
| 出典層(Issue 本文) | 保証しない — 外部所有・可変 | 内容の恒久性、行番号の安定性 |
| 引用層(三点併記 R-1〜R-3) | 改稿後の再解決可能性と、改稿の検出可能性 | 改稿された内容の自動追随 |
| 写像層(business-logic-model.md §4) | 判定の record 内固定 = 受入検査の外部非依存 | 出典が後に変わった場合の写像の妥当性(その場合は再判定でなく上流の裁定が要る) |
| 検査層(A1〜A5 + R-5/R-6) | 台帳が写像層と一致することの機械検出 | 写像層自体の正しさ(上流成果物の責務) |

各層は上位層の正しさを前提とし、自層の逸脱のみを検出する。全層を貫く「構造的保証」は存在しない。
