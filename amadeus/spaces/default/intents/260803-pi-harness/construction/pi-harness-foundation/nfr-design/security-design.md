# Pi Harness Foundation — Security Design

## 適用範囲

本設計のengine-resolved `consumes` は空であり、条件付きの `security-requirements` / `tech-stack-decisions` も非適用である。したがって新しい要件を作らず、Pi用authored harness、manifest、project-local resource discovery、question annex、canonical stage entry、生成candidateというfoundation境界だけを保護する。

対象外はlifecycle event処理、child RPC process、setup transaction、doctor probe、formal evidence、provider credential管理である。これらの所有 Unitへfoundation固有のsecurity logicを重複させない。

## Trust model

### Native project trust

Piのproject trustを、project-local `.pi/settings.json`、Pi Package、extension、skill、prompt/resourceをloadする前の唯一のhuman authorization boundaryとする。

- setup CLIはresourceをprojectへ配置できるが、Pi trust storeを編集しない。
- extension/bootstrapは`--approve`を自動付与せず、未trust projectでworkflow-changing operationを起動しない。
- `--no-approve`またはuntrusted状態ではproject-local resourceが見えないことをfailureではなくnative trust decisionとして扱い、read-only remediationだけを返す。
- trustはsandboxではない。承認後のextensionは同一OS user権限で任意コードを実行でき、skillはモデルへtool実行を指示できる。
- ancestor/global trustの解釈はPi本体へ委譲し、foundationが独自trust cacheや承認判定を持たない。

### Trust zones

| Zone | Trust level | Allowed transition |
|---|---|---|
| Authored source | repository review済み | packagerがmanifestをparse |
| Trusted expected catalog | build時にverifierへ束縛 | projection/doctor/testがread-only参照 |
| Generated `dist/pi` | observed output | expected catalogとの完全一致後だけ配布候補 |
| Target project | user-controlled/untrusted | transaction Unit経由でのみwrite |
| Pi runtime | trust decision owner | trust後だけproject-local resourceをload |

generated output、target install manifest、Pi settingsをexpected catalogの正本に昇格させない。

## Manifest と catalog integrity

### Authored manifest parsing

`PiHarnessManifest`はclosed schemaでparseし、unknown fieldを無視しない。最低限、harness identity、harness directory、resource kind、authored source、destination、generation owner、canonical `stageEntry`、minimum Pi versionをtyped valueへ変換する。

- harness nameはexact `pi`、harness dirはexact `.pi`。
- resource kindはclosed union（skill、extension、driver、question annex、package metadata、shared core projection）。
- source/destinationはnormalized repository-relative path。
- resource IDとdestinationは一意。Unicode normalization、case-fold、path separator差によるcollisionを拒否する。
- stage runnerは共通compiled graphのcanonical `stageEntry`だけを参照し、Pi固有のpath推測を持たない。
- version floorはsemverとしてparseし、文字列比較やinstall path labelから導出しない。

### Trusted expected catalog

packagerはauthored manifestとcore inventoryからcanonical sortした`PiHarnessExpectedCatalog`を生成する。catalogはschema version、framework distribution version、source revision、resource ID/path/kind/content digest、payload digestを持つ。

consumerは実行中moduleに束縛されたexpected catalog digestと完全一致するartifactだけを受理する。次を禁止する。

- observed `dist/pi`から期待resource集合を再構成する。
- target install manifestに無いentryを期待集合から除外する。
- resourceとmanifest entryを同時削除して一致扱いにする。
- catalog取得不能時にbuilt-in最小集合へfallbackする。

catalog missing、schema/version/digest mismatchはPi foundation全checkをblockedにし、部分resourceを成功扱いしない。

## Path と filesystem controls

### Source resolution

各resourceはauthored source rootを基準に解決する。

1. path文字列をUTF-8、NULなし、absoluteなし、空segmentなしのrelative pathへparseする。
2. lexical normalization後に`..` escapeが無いことを確認する。
3. source componentを`lstat`し、symlink、device、socket、FIFO、directory-as-fileを拒否する。
4. `realpath`がsource root内に留まることを確認し、regular file identityをsnapshotする。
5. hash計算とread後にfile identityを再確認し、途中差替えを`source-changed-during-projection`として失敗させる。

symlinkをresourceとして配布しない。link先がroot内でも、packagerとtargetで意味が変わるためregular fileへ正規化せず拒否する。

### Destination safety

destinationは`.pi/`または明示されたproject-root managed file内に限定する。absolute、root escape、reserved installer metadata、target `package.json` overwrite、duplicate/case-fold collisionを拒否する。foundationはtargetへ直接writeせず、validated candidateをtransaction Unitへ渡す。

## Resource execution risk

### Extension

Pi extensionはload時から同一user権限でコードを実行できる。次を必須とする。

- authored sourceとgenerated bytesのdigest一致。
- package metadataが宣言するextension entryとcandidate catalogの双方向一致。
- trust前の明示loadやCLI `-e`によるfoundation bypassを導入しない。
- dynamic download、runtime self-update、remote code fetchをextension bootstrapへ置かない。
- lifecycle extensionの能力欠落をadvisory/single-agent successへ縮退させない。

### Skill / question annex

skillはコードではないがモデルへ強い命令を与えるため、resource integrityの対象にする。

- skill frontmatter/name/pathをcatalogと照合する。
- stage runnerは共通stage fileとcompiled graphへ解決し、任意pathをpromptから実行しない。
- question annexはgate/presence意味論を緩和せず、Pi表示形式だけを定義する。
- generated promptへcredential、home path、machine-specific provider設定を埋め込まない。

## Supply-chain boundary

foundationはnpm publishを行わない。Pi Package local/git sourceはdistribution Unitが同じcandidateへ投影するが、foundation catalogは次のprovenanceを提供する。

- authored repository/source revision
- manifest/catalog schema version
- normalized resource digest集合
- generator identity/version
- minimum Pi version/platform policy

git sourceの正式手順はimmutable commit/tag pinを要求し、moving branchをformal evidenceのidentityにしない。source review、pin、update diff、uninstallは利用者guideで必須factとして説明する。

private registry token、SSH private key、provider credentialをmanifest/catalog/generated resourceへ含めない。package managerがdependency install scriptを実行し得るriskは隠さず、trustがsandboxでないことと併記する。

## Generated surface と drift

`dist/pi`、self-install、package viewはauthored sourceからのみ再生成する。生成済みtreeを手編集して正本へ戻すreverse importを持たない。

security drift guardは次を双方向検査する。

1. expected catalogとgenerated filesのmissing/extra/path/kind/hash。
2. generated package metadataとresource catalog。
3. harness discovery registryとmanifest discovery。
4. canonical stageEntryと全stage runner projection。
5. same source/configでの連続2回生成digestとsecond-run diff。

unknown extra fileもfailureにする。隠しfile、backup、editor temp、unexpected executableを配布候補へ黙って含めない。

## Data exposure controls

foundation artifactはsource pathをrepository-relative表現で持つ。diagnosticやcatalogへ次を入れない。

- home absolute path、username、machine-local installation root
- provider token/API key/OAuth/SSH private key
- user prompt、workflow artifact本文
- Pi user-level settings/trust decisionの内容

hashはsecret maskingではないため、secretをhashしてcatalogに載せることも禁止する。errorはresource ID、relative path、expected/observed digest prefix、remediationだけを含む。

## Failure policy

| Failure | Result | Mutation/load policy |
|---|---|---|
| manifest schema/path invalid | typed manifest failure | generation 0 |
| source symlink/root escape/type mismatch | typed source failure | generation 0 |
| source changed during read | typed snapshot failure | candidate publish 0 |
| expected catalog unavailable/mismatch | foundation blocked | fallback/load 0 |
| generated missing/extra/hash mismatch | drift failure | install candidate不適格 |
| untrusted project | native trust pending | auto-approve/workflow mutation 0 |
| Pi version/platform unsupported | typed compatibility failure | formal workflow start 0 |
| registration missing | parity failure | silent harness omission禁止 |

errorをcatchしてresourceを省略した「部分candidate」を成功として返さない。

## Threat matrix

| Threat | Control | Negative verification |
|---|---|---|
| project-local codeをtrust前load | native trust only、autoapproveなし | fresh untrusted fixtureでextension effect 0 |
| path traversal / symlink | typed relative path、lstat、root realpath | absolute/`..`/symlink/device拒否 |
| resource+manifest同時削除 | verifier-bound expected catalog | both deleteでmissing failure |
| generated tree改ざん | authored→generated one-way + digest parity | dist byte変更でcheck failure |
| registry omission | discovered manifest/catalog set parity | Pi entry削除mutationでfailure |
| malicious extra extension | unknown extra reject | generated/target extra entryでfailure |
| stage path injection | canonical `stageEntry` only | runner path改変でdiscovery failure |
| credential混入 | secret-free schema、repository-relative diagnostic | canary corpusでcatalog/dist 0件 |
| unsupported runtime受理 | semver/platform typed policy | Pi 0.82/native Windows positive=0 |

## Verification gate

最低限、次のproduction pathを使う。

- manifest parserへvalid candidate、absolute/escape/NUL/case-fold duplicate/unknown fieldを入力する。
- real filesystemでsymlink、hardlink/source swap、non-regular fileを検証する。
- clean fixtureでtrust前effect 0、明示trust後resource catalog一致を確認する。
- expected catalogを保持したままresource+observed manifest entryを同時削除し、必ずredにする。
- registration/stageEntry/generated package metadataを一件ずつmutateし、各guardがredになることを確認する。
- package generationを連続2回行い、normalized digest一致とsecond-run diff 0を確認する。
- secret/home canaryをauthored metadataへ混入し、schema/redaction guardがcandidate publish前に拒否する。

検査結果は実file set/hash/trust後resource discoveryから導出し、manifest内の自己申告`valid` fieldや固定件数を根拠にしない。
