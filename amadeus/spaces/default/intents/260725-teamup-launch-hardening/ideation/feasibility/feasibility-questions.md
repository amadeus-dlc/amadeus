## Q1: 検証再有効化に伴う待機設計

実験2で 1メンバーの arming に **32.2秒**（コールドスタート含む）を要することが判明した。actas 移行で検証が再有効化されると、`verify_watchers_armed` が `mux_attach` の前に最も遅いメンバーの arming 完了まで待つ構造が復活する。これは前 intent（PR #1477）が 200.85秒 → 5.87秒として解消した当の問題である。

どの待機設計を採るか。

- A. **検証を `mux_attach` の後ろへ移す**。アタッチは worktree 作成時間（並列化後 3.3秒前後）で完了し、検証はその後に走る。exit code の意味づけを再設計する必要がある。
- B. **検証をバックグラウンド化**し、結果を別経路（ログ・後続コマンド）で通知する。アタッチも exit code も現行のまま保てるが、通知経路の新設が要る。
- C. **検証は `mux_attach` 前のまま、タイムアウトを実測ベースへ縮める**（例: 32.2秒に余裕を見た 45秒 × 1ラウンド）。構造は最小変更だが、正常系でも数十秒のブロッキングが残る。
- X. Other (please specify)

[Answer]: A（ユーザー直接裁定 2026-07-25T11:20Z、ソロモードにつき選挙なし）。検証を `mux_attach` の後ろへ移す。採用理由: 実測 32.2秒/1メンバーの arming を `mux_attach` 前に待つと、前 intent(PR #1477)が 200.85秒→5.87秒として解消した起動レイテンシ問題を再導入する。後方へ移せばアタッチは worktree 作成時間(並列化後 3.3秒前後)で完了し、#1384 の保護と起動の速さを両立できる。C(タイムアウト縮小)は正常系でも数十秒のブロッキングが残り、B(バックグラウンド化)は通知経路の新設を要する。exit code の意味づけ再設計は requirements で確定する。
