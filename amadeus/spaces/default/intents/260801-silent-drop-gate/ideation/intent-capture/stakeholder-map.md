# Stakeholder Map — 260801-silent-drop-gate

## ステークホルダーと関心

| ステークホルダー | 種別 | 関心・影響 |
|---|---|---|
| フレームワーク開発者（本リポジトリ開発チーム） | 主要受益者 | 無音化違反が PR 時点で CI fail になり、後追い修正・人力棚卸しから解放される。CI 実行時間への影響は最小限であることを期待 |
| Amadeus ユーザー（導入ワークスペースのチーム） | 主要受益者 | コア配布物のランタイム fail-closed 化により、監査行の欠落や state の無音不整合が「起きたら止まる」ようになる。record/audit の信頼性が上がる |
| ワークフロー承認者（本 intent のゲート承認者） | 決定者 | 各ステージの承認ゲートで方向性を裁定。成功指標の実証を確認して完了を判断 |
| レビュー bot / CI 基盤（CodeRabbit, GitHub Actions） | 影響を受ける基盤 | ast-grep ルール追加と lint ジョブへのゲート組込み。CodeRabbit の ast-grep 連携設定と整合させる必要がある |
| 関連バグ Issue のウォッチャー（#1878/#1963/#1874/#1906） | 関係者 | 3件は本 intent で修正されクローズ。#1906 は別 intent として引き続き追跡される |

## 決定者 vs インフルエンサー

- **決定者**: ワークフロー承認者（ゲート承認）、フレームワーク開発者（実装判断）
- **インフルエンサー**: レビュー bot の指摘（過去の無音化指摘の実績）、先行ゲート設計（#528 の ratchet/allowlist 方式、callsite-guard のパターン）

## コミュニケーション要件

- ゲートの検出ルール・免除方法（`intentional-drop` マーカー）・ベースライン運用は、開発者向けドキュメント（AGENTS.md / docs/reference）に明記する
- 関連バグ3件の修正完了時は各 Issue をクローズし、#1979 の受け入れ基準との対応を本文に記録する
- 成功指標の実証結果（CI fail の実測、ベースライン単調減）は build-and-test ステージの成果物として記録する
