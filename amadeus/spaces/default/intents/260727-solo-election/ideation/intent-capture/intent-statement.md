# Intent Statement — solo-election

上流入力(consumes 全数): なし(本ステージは consumes を宣言しない — 入力はユーザー記述、intent-capture-questions.md の裁定 Q1-Q6、および承認系譜として引用する D-12 裁定)

## Problem Statement(解決する問題)

Amadeus のソロモードは現在、未決の判断をすべてユーザーへエスカレーションする。チームモードが持つ「独立検証された合意で判断する」(P1)機構 — エージェント選挙 — がソロモードには存在しないため、ユーザーが単一の裁定点となり、判断の負荷が集中する。一方、選挙 TS 基盤(260718-election-ts-foundation)は D-12 裁定(2026-07-19T01:35:00Z、decision-log:20)で**ソロ選挙の取り込み**を既に決定しており、輸送抽象(team=agmsg メンバー / solo=spawn サブエージェント)と票の `VoterKind = "member" | "subagent"`(amadeus-election-model.ts:126)まで実装済みである。欠けているのは輸送の solo 側ドライバと運用ノルムだけであり、本 intent はその**残余実装**である。

## Approval Lineage(承認系譜)

1. **D-12**(2026-07-19、ユーザー直接裁定): ソロ選挙を取り込む — 輸送抽象+VoterKind 属性明記。裁定の重みの解釈は消費側に委ねる。
2. **本日のセッション裁定**(2026-07-27、Grill me 全6問+合意サマリー確認済み): 発動条件・定足数2体・裁定効力・スケルトン・スコープ境界・GoA 2体適用表(下記)。

## Solution Vision(実現する姿)

ソロモードで main agent が**選挙管理委員**となり、fresh subagent 2体が**投票者**となる選挙形態を実装する:

- main agent は amadeus-election CLI で選挙を open し、blind ballot を **verbatim** で 2 subagent へ配布する(自身の分析・推奨を同梱しない。transport 層の構造的 blind は既存のまま)。
- 各 subagent は fresh context で独立に証拠を実測し、**自身が Bash で CLI を実行して投票する**(main agent の代筆禁止 — record 上の投票者と実行主体を一致させる)。票は `voterKind: "subagent"` で記録される。
- main agent は**投票しない**(管理委員専任 — leader-no-work のソロ対応)。
- 開票・裁定は CLI の typed directive loop(cid:election-cli-canonical)が正。

## 裁定済みの設計パラメータ(Q1-Q6)

1. **発動条件(Q1=D)**: 設計逸脱・ブロッカー・§13 学習選定の3類型で自動発動。それ以外はユーザーの明示指示(「選挙にかけて」)で発動。仕様変更・エスカレーション正準リスト事項はユーザー専権のまま(選挙対象外)。
2. **定足数(Q2=X)**: **2体固定**。チームモードの偶数設計(スプリット時に人間裁定へエスカレーション)を保存し、コスト最小(コールドスタート×2)で「機械の合意が割れたら人間」を再現する。
3. **裁定効力(Q3=A)**: 2-0 一致は即採用・続行(チームモードと対称)。裁定は record と監査に固定され、ユーザーは事後追跡できる。
4. **スケルトン(Q4=A)**: 実選挙1件の end-to-end 完走(open → 2 subagent spawn → 各自 CLI 投票 → 開票 → record 固定)+2-0(即採用)/1-1(エスカレーション発火)両分岐の実証。
5. **スコープ(Q5=A)**: ソロ輸送ドライバ(CLI verb ギャップ+amadeus-election SKILL.md のソロ分岐)+team.md ソロモード節のノルム改定を同梱。
6. **GoA 2体適用表(Q6)**: GoA 8段階スケールと既存集計規則は不変のまま、2体への適用を確定する —
   - 両票 1-3/6(賛成側)→ 2-0 成立・即採用(2/3/6 票の留保1文転記は必須のまま)
   - 賛成1・反対(7-8)1 → スプリット → ユーザーエスカレーション
   - 8(ブロック)1票 → 成立保留 → エスカレーション(反証可能な根拠必須も不変)
   - 5(追加議論)1票以上 → 追加議論ラウンド1回(2体では閾値を1票へ引き下げ)。再投票後も 5 残存ならエスカレーション
   - 4(棄権)1票 → 残1体では成立不能 → エスカレーション(単票を裁定に昇格させない — P1 保存)

## Target Customer(誰が恩恵を受けるか)

- **ソロモードのユーザー**(第一受益者): 3類型の判断がまず 2体選挙で処理され、割れたケースだけが裁定に上がる。裁定負荷が「全件」から「不一致・ブロック・棄権ケース」へ縮む。
- **conductor(main agent)**: 判断に迷う場面で「ユーザーを待つ」以外の正規手段を得る。
- **チームモードの運用**: 変更なし(既存の member 投票経路・GoA 規則は不変)。

## Success Metrics(成功指標)

1. スケルトン選挙1件が end-to-end で完走し、`voterKind: "subagent"` の票 2 票が elections store に固定される(実測)。
2. 2-0 分岐: 裁定が即採用され record に固定される。1-1 分岐: ユーザーエスカレーションが発火する(両分岐とも実証必須 — 落ちる実証を含む)。
3. team.md ソロモード節の改定が同一 intent で着地し、機構とノルムの乖離期間がない。
4. 既存のチームモード選挙(member 経路)のテストがすべてグリーンのまま(無退行)。

## Out of Scope(除外)

- 質問への推奨自動選択機構 — standing grant の射程外と確認済み、導入しない

- チームモード選挙の挙動変更(定足数・GoA 規則・agmsg 輸送)

## Risks & Assumptions(リスクと前提)

- **仮説**: fresh subagent 2体の票は実用上十分に独立である(コンテキスト独立+自前の証拠実測)。配布 verbatim 規律とプロンプトの中立性が前提。
- **リスク**: subagent が CLI 投票を完遂せずターン終了する(既知クラス — cid:builder-prompt-sync-completion)。ディスパッチプロンプトに同期完遂の定型文言を含めて抑止する。
- **リスク**: 2体という最小定足数では、同一モデル由来の相関誤りが 2-0 一致として通る可能性がある。緩和: 発動3類型は反証可能な証拠ベースの判断に限られており、票には根拠(rationale)と GoA が必須。運用実績を見て体数・多様性を再裁定できる(Q2 は「2体固定」だが将来のノルム改定を妨げない)。
- **前提**: Agent tool(subagent spawn)が利用可能なハーネスで動作する。spawn 不能なハーネスでは従来どおり全件ユーザーエスカレーション(降格は loud に告知)。
