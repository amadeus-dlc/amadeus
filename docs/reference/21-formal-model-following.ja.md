# 形式モデルを実装に追従させる

> 言語: [English](21-formal-model-following.md) | **日本語**

`specs/tla/` の TLA+ モデルは、それが記述していると主張するコードを実際に記述している間だけ価値を持ちます。`specs/tla/model-map.json` は各モデルを、その導出元となった実装ファイルへ pin し、`model-completeness` sensor は監視対象パスに触れるたびにその pin を再計算します。pin が一致しなくなると、sensor は drift を報告します。

本章はその次に何をするかを扱います。drift は判定ではなく問いです。sensor はバイト列が動いたことは見えますが、**意味**が動いたかどうかは見えません。それに答えるのは開発者の仕事であり、どちらの方向へ誤っても代償があります。モデル改訂を要する変更で hash だけを更新すれば、静かに嘘をつくモデルが残ります。逆に単なるリネームでモデルを改訂すれば、完全探索1回分を無駄にします。

まだモデルを持たないプロトコルへモデルを書く工程は [新規プロトコルへ形式モデルを供給する](22-formal-model-supply.ja.md) を参照してください。

## drift シグナル

`model-completeness` は `specs/tla/model-map.json` を読み、pin された全実装エントリの SHA-256 を再計算し、不一致を報告します。map・モデル・設定・実装のいずれも変更しません。自分のシグナルを自分で修復する検出器は、何かが起きたことを伝えられなくなるからです。

finding は repository 相対パスと固定の理由コードのみを含みます。hash・ファイル内容・絶対パスは意図的に除外されます。

ここには2つの異なる条件が現れ、両者は互換ではありません。

- **実装 drift** — pin された実装ファイルが変わった。モデルと設定は無変更。
- **`SOURCE_DRIFT`** — モデルまたは設定のバイト列自体が変わった。実行**中**に起きる場合もあります。model-check toolchain は、module または `.cfg` の identity が計画時と spawn の間、あるいはプロセス境界を跨いで変化した場合にもこれを上げます。実際に検査されたバイト列以外へ verdict が帰属することを防ぐためです。

## どちらの分岐かを決める

実装変更について問いは1つです。**その変更は、モデルの invariant が及ぶ振る舞いの集合を変えうるか?**

答えは、そのモデル自身の縮約申告に対して diff を読むことで出します。`specs/tla/` の各モデルは冒頭のコメントブロックで、実装のどの部分を捨象したかとその理由を宣言しています。申告が既に捨てている部分に閉じた変更は、モデルが証明する内容を変えられません。ガード述語・status 値・dispatch の分岐、あるいは申告が本質的と名指しした状態フィールドへの変更は変えうります。

具体的には次のとおりです。

| 変更内容 | 分岐 |
| --- | --- |
| リネーム・コメント・整形・型のみの編集 | 実装のみ |
| 到達可能状態を増やさないリファクタ | 実装のみ |
| ガード述語の新設・変更 | モデル改訂 |
| transition kind・status・operation の追加 | モデル改訂 |
| 縮約申告が捨象したフィールドが本質的になった | モデル改訂 |

判断できないときはモデル改訂の分岐を取ります。その代償は完全探索1回ですが、実装のみの分岐の失敗様式は「もはや記述していないコードについて成功を報告するモデル」です。

## 分岐 A — 実装のみの変更

pin は stale ですがモデルは成立しています。モデルに触れず実装 hash だけを更新します。

```
bun .claude/tools/amadeus-sensor-model-completeness.ts updateModelMap --impl-only
```

`--impl-only` は、この場合に `model-map.json` の手編集ではなく**記録の残る**経路を与えるために存在します。モデル意味論に影響しない旨の明示宣言を要求し、モデルまたは設定の identity も変わっている場合は実行を拒否し、後から帰属を辿れるよう監査行を書きます。フラグなしで同じコマンドを実行すると `MODEL_UNCHANGED` として更新は拒否されます。実装 pin の更新はフラグなし経路の用途ではないからです。

宣言こそがこのフラグの要点です。「誰かが JSON を編集した」を「特定の人物がこの日付に、この diff は意味論的に不活性だと表明した」へ変換します。レビュアーが実際に検証できるのは後者だけです。

## 分岐 B — モデル改訂

実装の意味が動いたので、モデルも動かします。

1. **モデルを更新する。** 変わったガード・transition・ドメインを `.tla` module へ翻訳します。各演算子が翻訳した述語を指す `file:line` の出典コメントは維持します。
2. **縮約申告を更新する。** 捨象してよい範囲が変わった場合です。新しい transition が存在する前には健全だった縮約が、その後も健全とは限りません。新しい論拠を縮約ごとに申告へ書きます。
3. **完全探索を再実行し、完走を確認する。** 部分探索はエビデンスになりません — [形式モデルの供給](22-formal-model-supply.ja.md#完走こそがエビデンス) を参照。
4. **map を更新する。** `--impl-only` なしで `updateModelMap` を実行します。モデルと設定の identity は実際に変わっているので、通常経路が適用されます。
5. **モデルと実装を同時に着地させる。** 片方だけを動かすコミットは、誰も対処できない理由で sensor が赤い状態をツリーに残します。

再実行が失敗するようになったなら、それはモデルが仕事をしています。モデルが誤っていると決めつける前に反例を読んでください。実装変更後に invariant が落ち始めるのは、リグレッションが捕まった際の期待どおりの形です。

## sensor に分からないこと

- **pin されていないファイルは監視しません。** `matches` glob と `model-map.json` の `entries` が、監視面を共同で定義します。モデルが依存していながら誰も pin しなかったロジックは、無音のうちに変わります。モデルが新しいファイルの述語を翻訳し始めたら、同一変更でそのファイルを `entries` へ追加してください。
- **モデルが忠実かどうかは検査しません。** 検査するのは、導出元のバイト列が動いていないことだけです。忠実性はモデルを書く時点で確立し、申告が変わるたびに論じ直します。
- **TLC は実行しません。** drift 検出は安価で毎回走り、完全探索は高価で `formal-model-check` ステージで走ります。drift 検出が green であることは pin の一致を意味し、invariant の成立を意味しません。
